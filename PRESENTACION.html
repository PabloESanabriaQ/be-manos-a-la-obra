Gestor de Proyectos

Gestión jerárquica de proyectos ágiles

Node.js · Express MongoDB · Mongoose React · Vite JWT + Refresh tokens Swagger / OpenAPI

Backend REST + SPA en React · Pablo Sanabria

¿Qué es Gestor de Proyectos?

Una aplicación web para gestionar proyectos siguiendo una jerarquía inspirada en metodologías ágiles, con tres roles y permisos diferenciados.

Proyecto └─ Épica └─ Historia de Usuario └─ Tarea

Cada nivel tiene CRUD completo. Las historias soportan estimación con story points Fibonacci (planning póker), asignación de responsables y filtrado por estado.

  1. Route declara endpoint + middlewares.

07 · API

Autenticación: JWT + refresh tokens

Cookies HTTP-only

  • token — JWT firmado, 15 minutos.
  • refreshToken — 64 bytes aleatorios, 7 días, persistido en BD.
  • En producción: Secure + SameSite=none.
  • Inaccesibles desde JS → mitiga XSS.

Rotación

  • Cada /auth/refresh elimina el viejo y emite uno nuevo.
  • /logout elimina el refresh token del usuario.
  • Rate limit: 10 intentos / 15 min en login.
// middlewares/authentication.js — verificación por request
const decoded = jwt.verify(token, JWT_SECRET);
const user = await User.findById(decoded.id, 'role active');
if (!user)          return res.status(401).end();
if (!user.active)   return res.status(403).end(); // cuenta desactivada
req.userId   = decoded.id;
req.userRole = user.role;

errorHandler = (err, req, res, _next) => {
  const status = err.status || 500;
  status >= 500
    ? logger.error({ err }, err.message)
    : logger.warn ({ err }, err.message);
  const body = {
    error: true,
    name: err.name,
    message: err.message,
  };
  if (err.code)   body.code = err.code;
  if (err.params) body.params = err.params;
  res.status(status).json(body);
};

Validadores por recurso en utils/: validateCreateStory, validateUpdateTask, etc. Sin Joi/Zod, manteniendo dependencias livianas.

i18n del cliente: los errores pueden llevar { code, params } (por ej. INVALID_POINTS) y el frontend los traduce con errors.<code> según el idioma.

15 · Estado global

Cliente HTTP y patrón de servicios

apiFetch()

  • Prefija VITE_API_URL.
  • credentials: "include" siempre.
  • En 401: intenta /auth/refresh y reintenta una vez.
  • Si falla: limpia localStorage y redirige a /.

Convención

  • GET → custom hook { data, loading, error }.
  • Mutaciones → función async que lanza errores.
// services/getAllProjects.js
export default function useAllProjects() {
  const [data, setData]       = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError]     = useState(null);
  useEffect(() => {
    apiFetch("/projects")
      .then(({ data }) => setData(data))
      .catch(setError)
      .finally(() => setLoading(false));
  }, []);
  return { data, loading, error };
}

19 · Calidad

Husky + lint-staged en el frontend

Qué corre en cada commit

"lint-staged": {
  "*.{js,jsx}": [
    "eslint --fix",
    "prettier --write"
  ],
  "*.{css,scss,json,md}": [
    "prettier --write"
  ]
}
  • Solo corre sobre archivos staged, no toda la base.
  • Re-stagea los autofixes y deja el commit limpio.
  • Si algo no se puede arreglar, el commit aborta.

Para qué sirve

  • Lint automático — vars sin uso, semis, comillas, reglas de hooks: corregidos sin pensar.
  • Formato consistente — Prettier neutraliza diferencias de editor entre quienes contribuyen.
  • Falla rápido — el ruido se ataja antes del PR, no en code review.
  • Sin penalidad — solo toca lo modificado, típicamente menos de 2 segundos.

El backend no tiene hooks instalados: .husky/ no existe y package.json no declara "prepare". Linteo confiado al editor + revisión manual.

20 · Husky

Decisiones de diseño — seguridad y dominio

  • Permisos en dos niveles — un rol global (admin_users) separado del rol que cada usuario tiene dentro de cada proyecto. Aísla la administración del sistema de la operación cotidiana.
  • Cookies HTTP-only para JWT — el frontend nunca toca el token (mitiga XSS). La "sesión lógica" se infiere de localStorage.user.
  • Refresh token rotativo — cada uso emite uno nuevo y elimina el viejo, acotando la ventana de un token robado.
  • Soft delete en cascada implementado en servicios (no en hooks de Mongoose) — control explícito sobre el orden y testeable sin levantar la base de datos.
21 · Decisiones I

Decisiones de diseño — DX y producto

  • Servicios GET como hooks con firma { data, loading, error } — estandariza la lectura asincrónica y elimina boilerplate repetido en cada vista.
  • Mutaciones como funciones async que lanzan errores — el llamador decide cómo mostrarlos (ErrorToast, redirección, etc.).
  • Sin Joi/Zod ni librerías pesadas de auth — validadores propios en utils/, dependencias livianas y transparencia pedagógica.
  • i18n y dark mode de primera clase desde el inicio, no añadidos tardíamente. Cada string visible pasa por t("clave"); el tema usa CSS custom properties intercambiables vía data-theme.
22 · Decisiones II

Trabajando con IA: leer el código que genera

En MyStoriesView, cada cambio de pestaña (Todas / Por hacer / En curso / Hecho) disparaba un GET a /stories. La IA había sumado status como dependencia del useEffect: técnicamente funciona, pero es ineficiente.

Antes — refetch en cada click

function PMStoriesView() {
  const [status, setStatus] = useState(null);
  const { data, loading, error } =
    useAllStories({ status });   // ← refetch

  return <List data={data} />;
}

Después — filtro en memoria

function PMStoriesView() {
  const [status, setStatus] = useState(null);
  const { data, loading, error } = useAllStories();

  const filtered = useMemo(
    () => status
      ? data?.filter(s => s.status === status)
      : data,
    [data, status],
  );
  return <List data={filtered} />;
}

Moraleja: la IA acelera, pero hay que revisar lo que escribe y conocer el stack — useMemo, dependencias de useEffect, costo de I/O — para distinguir "funciona" de "funciona eficientemente". Una request por click ≠ una request por carga + filtrado local.
